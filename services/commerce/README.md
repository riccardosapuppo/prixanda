# Engine

The commerce engine: the rules of the business book (`docs/business.md`) in
Python 3.13, over PostgreSQL 18, behind the gRPC contract of `proto/`. It
keeps the price list, the changes and their approvals, the launches that put
them live, the quotes and subscriptions of the site, and the audit log. The
gateway is its only caller on a server; in the demo in the browser the same
code runs in Pyodide on PGlite (`packages/sandbox`).

The engine is the trusted layer (§7.4): it checks on every call who acts and
in which role, and the database checks the rules a third time, with
constraints and triggers of its own.

## What is where

| Path | What |
|---|---|
| `src/commerce/domain` | the rules as plain Python, with no database and no I/O: money and VAT, local times across a change of the clocks, offers and their validation, the artists' economics (§5), the sentences a change is described in, the policies of each market, price migrations, prepaid passes, the audit chain's walk |
| `src/commerce/engine` | the services, one method of the contract each, behind one entrance (`engine.py`) that checks the caller, the idempotency key and the transaction; the launches (`launches.py`), the outbox, the simulated payment provider and student check, and the jobs (`jobs.py`) |
| `src/commerce/engine/database.py` | the engine's door to the database: a small interface of plain values, which `adapters/asyncpg_database.py` implements on asyncpg and `browser/pglite.py` on PGlite |
| `src/commerce/server` | the gRPC server (grpc.aio): the internal token, the status codes, the health protocol, the jobs' timer, the configuration, the orderly stop |
| `src/commerce/v1` | the contract's messages, generated by `npm run proto` |
| `src/commerce/generate.py` | the generator of the synthetic data |
| `src/commerce/invariants.py` | the invariants of the data no single constraint can hold |
| `src/commerce/measure.py` | the queries that matter on the full data (§14.2), measured before and after migration V16 |
| `src/commerce/compat.py` | the change of schema in two times (V12, then V14), with the version before it still working |
| `src/commerce/browser` | the package for the browser: the PGlite adapter, the entrance the page calls, the build's writer of the data |

The schema is in `db/migrations`, applied by Flyway (V1 to V17). Its triggers
raise codes of their own, RL001 to RL013, each explained in the migration
that defines it.

## Running it

```
npm run engine
```

It starts the development database if it is not running (`.data/postgres`
on 127.0.0.1:4601, `DEV_POSTGRES_PORT`), applies the new migrations with
Flyway, loads the small generated data the first time (seed 7), finds or
creates the internal token (`proto/README.md`, convention 4), and runs the
server on 127.0.0.1:4611 (`ENGINE_URL`). Ctrl+C stops the engine in order;
the database keeps running until `npm run db -- stop`. `npm start` runs the
whole system instead: the engine, the gateway, the console and the site.

The server reads its configuration from the environment; the two secrets,
the database URL and the token, are never written to a log.

| Variable | What | Default |
|---|---|---|
| `COMMERCE_DATABASE_URL` | the database, as the engine's role (`commerce`) | required |
| `COMMERCE_INTERNAL_TOKEN` | the token the gateway sends, at least 32 characters | required |
| `COMMERCE_ENGINE_HOST`, `COMMERCE_ENGINE_PORT` | where it listens | 127.0.0.1, 4611 |
| `COMMERCE_DB_POOL_SIZE` | connections to the database | 10 |
| `COMMERCE_ACTIVATION_INTERVAL_SECONDS` | seconds between two passes of the jobs | 5 |
| `COMMERCE_HEALTH_INTERVAL_SECONDS` | seconds between two checks of the database | 5 |
| `COMMERCE_SHUTDOWN_GRACE_SECONDS` | what the running calls get to finish, at a stop | 10 |
| `COMMERCE_STOP_ON_STDIN_CLOSE` | 1: stop when standard input closes, for a supervisor | off |

## The jobs

The engine's own work, outside any call, in one pass at a time
(`engine/jobs.py`): the launches of the changes that are due (§7.5), the end
of offers and passes whose periods are over, the expiry of prepaid codes not
used (§9), the end of price migrations' windows (§8), the outbox's
deliveries (the site's notice, the charges, the listeners' requests) and,
every hour, the pruning of idempotency keys older than a week. A pass runs
at the start, which resumes what a stop left halfway, then on the timer, and
at once after a call that left work for it. The log says each change of
state once, as one JSON line.

A launch runs five steps in order (check, prepare, publish, notify, verify),
each in its own transactions, so that a fault leaves a step done with all
its work or running with none of it, and the next pass resumes it. A step
that fails waits 5, 15, 45 and 135 seconds before its next attempts; after
five failures in a row the launch fails and opens an incident, and a change
not live five minutes after its start raises the alarm. `docs/runbook.md`
says what to do when a launch is stuck.

## The data generator

```
python -m commerce.generate --url <owner URL> --size small --seed 7
```

Deterministic: the same seed, size and period give the same rows, and
`--fingerprint` prints a hash of them, which the tests and the browser's
snapshot compare. Nothing reads the clock: the period is `--start` to
`--until`, 1 January 2025 to 24 October 2026 by default (`npm start` asks
for its own day). It writes the demo's people, by role (§12.1), the plans and
the price list at the start of the period (§2, §4.4), labels, artists and
releases, subscribers with their history and student verifications, the six
listeners the site's entrance offers (invented people, labelled as
simulated), and the last weeks of listening (§14.2).

| Size | Paying | Free | Artists besides the seven named ones | Days of listening |
|---|---|---|---|---|
| `small`, for the tests and the demo | 2,000 | 3,000 | 40 | 35 |
| `full`, for the measurements | 200,000 | 280,000 | 400 | 35 |

With the default period, `--size small --seed 7` writes 5,006 subscribers,
7,173 subscriptions, 936 student verifications, 47 artists and 108,924 rows
of listening, as the command prints them. `--listening-days` asks for a
longer history, for the measurements.

```
python -m commerce.invariants --url <URL> [--anchor <seq>:<hash>]
```

checks what no single constraint can hold, rules across tables or time, and
the audit chain, and exits 1 on a violation, with examples of each.

## Checks

```
npm run check -- --only pytest,data,compat,measure,sandbox-services,start
```

| Suite | What it proves |
|---|---|
| `pytest` | the engine against PostgreSQL 18, by area: the database's own rules (`tests/`), the domain, the business book's numbers as golden cases, every service with its refusals and errors, the calls over gRPC with a real server (`e2e`), the properties Hypothesis generates cases for, the faults injected in a launch with the engine's real process (`faults`), and the package for the browser (`browser`); a skipped test fails the suite |
| `data` | the small data generated, then every invariant on it |
| `compat` | the change of schema in two times: data written by the version before it, the expansion with that version still working, every later migration, the invariants, and this engine reading the same |
| `measure` | the measuring tool tried on the small data: each query gives the same answer before and after V16 |
| `sandbox-services` | the service tests, unchanged, on PGlite through the browser's adapter; those that need more than one database session are marked `postgresql_only` and left to PostgreSQL |
| `start` | `npm start` on the check's database, each address answering, and its orderly stop |

Each suite must reach the minimum written in `tools/check.ts`. The tests read
their database from the check (`COMMERCE_TEST_ADMIN_URL`,
`COMMERCE_TEST_TEMPLATE`, `COMMERCE_TEST_APP_URL`), each in a database of its
own cloned from a migrated template; `COMMERCE_TEST_DATABASE=pglite` runs the
service tests on PGlite (`tests/pglite_world.py`).

`npm run measure` measures the queries of §14.2 on the full data, on a
PostgreSQL of its own on 127.0.0.1:4650 (`MEASURE_POSTGRES_PORT`), and writes
the machine and the conditions beside the numbers in `reports/measure.json`.
⟨The numbers, measured on a machine doing nothing else.⟩

## In the browser

The domain, the services and the contract's messages run in the browser's
demo as they are, with `commerce.browser` beside them: the database is
PGlite, one session in the page's worker, and the engine's clock is the
demo's. What differs from the server, and how the browser gets its data,
is in `packages/sandbox/README.md`.
